# Segurança e privacidade

## O que a ferramenta lê e o que ela publica

- **Lê** (somente leitura) os registros locais de cada fonte (ver `docs/fontes-de-dados.md`). Usa apenas datas, contagens, tokens e o nome da última pasta do projeto. Texto de conversas, código, títulos e ids de sessão são descartados em memória.
- **Publica** exatamente cinco arquivos, planos na raiz do repositório de dados que você configurou (lista fixa no código, sem subpastas): `metrics.json` (agregado, esquema v1), `metrics.svg` (o modelo escolhido em `model`) e `metrics.model-1.svg`, `metrics.model-2.svg`, `metrics.model-3.svg`.
- **Nunca** vão para o JSON/SVG: texto de conversa, código, caminhos, nome de usuário do sistema, e-mail, ids de sessão, nomes de modelo.
- Os bancos SQLite das outras ferramentas (Cline, app do ChatGPT) são abertos com `readOnly: true`; um teste confirma que a opção é respeitada e que o arquivo não muda depois da leitura.

## Travas

1. **Allowlist estrita de campos e formatos** (`src/schema.mjs`): campo extra, texto livre, caminho e e-mail são rejeitados; ids de ferramenta reservados (`constructor`, `__proto__`...) também.
2. **Barreira de privacidade** (`src/privacy.mjs`): recusa caminho de disco, pasta pessoal, e-mail e nomes de arquivo de dados. Vale para o JSON, para o **título** (`title` da config e `--title`) e para o **SVG final**, antes de gravar ou enviar. O nome público (alias) também é validado: não pode ser igual ao seu usuário do sistema nem à sua pasta pessoal, nem parecer caminho, e-mail ou arquivo.
3. Projetos anonimizados por padrão; nomes públicos só pela lista em `config.json`, conferidos de novo no `publish`. A lista aceita o nome da pasta ou o **caminho completo** (`{"C:\\dev\\app": "app-pessoal"}`) para separar pastas homônimas; se mais de uma pasta distinta resolver para o mesmo nome público, `export`, `publish` (dry-run) e `report` avisam.
4. `publish` é dry-run por padrão e só envia com `--yes` ou confirmação interativa. Nunca usa `--force`.
5. **Envio automático amarrado ao que você aprovou.** O agendador (`run` sem terminal) só envia com `autoPublish: true` e depois de um `publish` manual confirmado **em terminal interativo** (`publish --yes` sem terminal envia, mas não conta como aprovação). A aprovação guarda, em `state.json`: os nomes públicos, o destino `{remoto normalizado, branch, commitName, commitEmail}` (nome e e-mail EFETIVOS do autor, inclusive o padrão noreply) e os pares `pasta -> nome público`. Se qualquer um mudar, o automático é **bloqueado** com a explicação do que mudou. Para reaprovar: rode `ai-usage-metrics publish` num terminal, confira o dry-run e confirme (vale mesmo quando nada mudou nos números). Estados antigos, sem destino ou sem autor registrado, também bloqueiam até a reaprovação.
6. **Remoto restrito.** Só `https://host/caminho` (sem usuário/senha/token), `git@host:caminho` e `ssh://git@host/caminho` (sem senha). A validação olha a string **crua**, antes de o parser de URL normalizá-la: só ASCII imprimível, `%` (codificação percentual) é recusado em qualquer posição do caminho, segmentos `.`/`..` são recusados, e hosts com rótulo `xn--` (punycode) são **recusados** (escolha mais segura: um domínio internacionalizado pode imitar outro; se você realmente usa um, rode o git manualmente). Recusados: `http://`, `git://`, `file://`, caminhos locais e UNC, `ext::`/`xyz::`, nomes começando com `-`, espaços e caracteres de controle. O git roda com `protocol.allow=never` e libera só `https` e `ssh`. Mensagens de erro e saídas nunca repetem a URL fornecida e removem `usuario:senha@` de qualquer texto do git. **Política de host:** só nome DNS público com ponto. São recusados `localhost` e `*.localhost`, nomes sem ponto (`servidor`), sufixos internos (`.local`, `.localdomain`, `.internal`, `.intranet`, `.lan`, `.home`, `.corp`), IPs literais IPv4 em qualquer notação (decimal `2130706433`, hex `0x7f000001`, octal, formato curto `127.1`) e qualquer host com um rótulo só numérico ou começando com `0x` (o `getaddrinfo` do sistema converte esses em IP); IPv6 já era recusado. Um host diferente de `github.com` (por exemplo um GitHub Enterprise seu) **é aceito**, mas o dry-run mostra um aviso destacado com o host; o envio automático continua amarrado ao destino aprovado. **SCP x ssh://:** `git@host:u/r` (caminho relativo ao HOME do servidor) e `ssh://git@host/u/r` (caminho absoluto) são destinos DIFERENTES: trocar de uma forma para a outra conta como mudança (bloqueia o automático até nova aprovação manual e faz o clone ser recriado, com aviso); a forma normalizada guardada em `state.json` é `scp://git@host/u/r`. (`AI_USAGE_METRICS_TEST_ALLOW_LOCAL_REMOTE=1` libera remoto local e é **somente para os testes**: é lida do ambiente do processo, nunca do `config.json`; não a defina no agendador nem no seu shell. Ela também deixa o git receber `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_NOSYSTEM` do ambiente, o que é só para isolar os testes.)
7. **Ambiente do git por allowlist.** O `git` recebe só variáveis neutras (PATH, HOME/USERPROFILE, temporários, idioma, `SSH_AUTH_SOCK`...). Não são repassadas `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_CONFIG_COUNT/KEY_n/VALUE_n`, `GIT_SSH_COMMAND`, `GIT_SSH`, `GIT_ASKPASS`, `GIT_EXEC_PATH` etc. Hooks do usuário não rodam no clone (`core.hooksPath` aponta para uma pasta vazia, mais `--no-verify` no commit e no push), assinatura automática de commit fica desligada e `core.symlinks=false`. Consequência: se o seu git depende de `GIT_ASKPASS`/`GIT_SSH_COMMAND` no ambiente, configure isso no `~/.gitconfig` (gerenciador de credenciais, `core.sshCommand`) ou na chave SSH padrão. O `~/.gitconfig` e o `/etc/gitconfig` continuam valendo (são seus): um `url.<x>.insteadOf` global é respeitado pelo git, e por isso a ferramenta compara a URL **crua** guardada no clone (`git config remote.origin.url`, sem aplicar `insteadOf`) com a URL aprovada, normalizando os dois lados; o envio também não deixa um `insteadOf` global quebrar o segundo `publish`. Um `insteadOf` global pode, é claro, redirecionar o destino: só o seu `~/.gitconfig` faz isso, a ferramenta não o cria nem o desativa.
8. **Clone em cache seguro.** Antes de qualquer comando git no clone, a ferramenta confere (com `lstat`) que `repo/` e `repo/.git` são pastas de verdade (`repo/` como link simbólico, junction ou arquivo é **recusado**, sem apagar nada; `.git` como link/arquivo `gitdir:` num clone nosso faz o clone ser **renomeado e recriado, com aviso**) e que o `.git/config` só tem as chaves que o `git clone` cria (`core.*` básicas, `remote.origin.url` e `fetch` padrão, `branch.*`). Qualquer outra chave (`remote.origin.pushurl`, `core.sshCommand`, `core.fsmonitor`/`editor`/`pager`, `url.*.insteadOf`/`pushInsteadOf`, `credential.*`, `include`, filtros, proxy...) significa clone adulterado: ele é renomeado (nunca apagado) e recriado, e nada dele é executado. O `remote.origin.url` cru precisa ser igual ao remoto aprovado depois de normalizar; se você mudar o remoto na configuração, o clone antigo também é recriado. Todos os comandos git usam `--git-dir`/`--work-tree` explícitos (nunca sobem para um repositório numa pasta-mãe) e o `push` vai para a URL aprovada, não para o nome `origin` (assim um `pushurl` nunca desvia o envio). Não passamos `-c core.sshCommand=` vazio nem `-c credential.helper=`: ambos quebrariam o ssh/gerenciador de credenciais que você configurou no `~/.gitconfig` (testado: `core.sshCommand` vazio dá `cannot spawn`); a defesa é a conferência da config LOCAL do clone. O clone e o `.git` precisam ser pastas de verdade; se `metrics.json`/`metrics.svg` forem link simbólico (no disco ou no repositório remoto, modo `120000`) o envio é recusado. A escrita é atômica (arquivo temporário exclusivo + renomear), nunca segue link.
9. **Uma execução por vez** por pasta de estado: um `.lock` (pid + hora) evita corrida entre `run` agendado e comando manual. Trava de processo morto, ilegível e antiga, ou com mais de 6 h é recuperada, sem corrida: uma guarda exclusiva (`.lock.reclaim`) serializa a recuperação, a trava é relida dentro dela e renomeada para um nome único antes de ser apagada, então um processo nunca apaga a trava nova do outro. A pasta de estado e os arquivos que a ferramenta grava (`config.json`, `state.json`, `history.json`, `out/metrics.json`, `out/metrics.svg`, `out/avisos.json`, `out/historico.json`) são criados com modo `0700`/`0600` em Linux/macOS (no Windows os modos POSIX não se aplicam: vale a ACL herdada do seu perfil de usuário; não verificado em Linux/macOS aqui); senão a mensagem diz quem a detém e qual arquivo apagar.
10. **Registros adversariais ou corrompidos** (arquivos locais podem ser editados por qualquer programa seu): datas só entre 2000-01-01 e amanhã (o resto é descartado com aviso, sem derrubar a execução); tokens só inteiros seguros até 1 bilhão por campo (o resto vira 0) e somas saturadas; arquivo `.jsonl` acima de 512 MiB é ignorado, linha acima de 16 MiB é descartada, `.messages.json` do Cline acima de 64 MiB é ignorado; `messages_path` do Cline só é lido se, resolvido o link simbólico, ficar dentro de `~/.cline` e for arquivo comum; mais de 4000 dias ou 1000 projetos degradam (ficam os mais recentes/ativos) com aviso. **Tetos de entradas distintas** antes desse corte, para um arquivo cheio de ids únicos pequenos não esgotar a memória: até 200 000 ids de resposta e 2 000 000 mensagens por arquivo do Claude Code, 10 000 pastas distintas no total (o excedente vai para "(sem projeto)"), cada caminho de projeto (`cwd`) com no máximo 4096 caracteres (acima disso o valor é descartado, a atividade vai para "(sem projeto)" e há um aviso agregado; nos bancos SQLite o corte é feito na própria consulta, e `aggregate` repete a trava para qualquer adaptador), 500 000 sessões distintas (eventos de sessões novas além disso são ignorados) e 200 000 linhas do catálogo do app do ChatGPT; sempre com aviso e sem derrubar a execução. Linhas de transcrição que não são objetos JSON (`null`, números, textos, listas) são ignoradas. O `avisos.json` (gravado na pasta `out/` do estado, nunca ao lado de `--out`) é lido com sequências ANSI/OSC e caracteres de controle removidos e cada aviso limitado a 300 caracteres. Nomes de pasta mostrados no `report` têm caracteres de controle trocados por `?`.
11. **A pasta `repo/` só é mexida se for nossa (marcador de posse).** Quando a ferramenta cria o clone, grava `<state-dir>/repo.owner.json` (`{tool, id aleatório de 128 bits, path real da pasta repo, createdAt}`) e copia o id para `repo/.git/ai-usage-metrics-owner`. Só um clone com marcador de fora válido, **amarrado ao caminho real** (um marcador copiado para outro state-dir não vale) e, se o `.git` é pasta, com a cópia interna igual ao id, pode ser recriado. Sem marcador, a ferramenta **não apaga nem altera nada** e recusa com erro claro pedindo para mover/renomear a pasta ou escolher outro `--state-dir` (vale também no modo automático); só uma pasta `repo/` vazia é aceita (o git clona dentro dela). Recriar um clone nosso divergente **renomeia** a pasta para `repo.velho-<timestamp>-<aleatório>` (com o marcador ao lado, em `repo.velho-….owner.json`) e avisa; são mantidas só as 3 mais recentes, e a poda apaga apenas pastas reais `repo.velho-*` que tenham marcador nosso válido. Clones criados por versões anteriores (sem marcador) também são recusados uma vez: renomeie a pasta `repo` e rode de novo. O `--state-dir` também é validado: raiz de unidade, a pasta pessoal inteira (do sistema e a de `--home`) e pastas que já são repositório git (`.git` no próprio nível) são recusados. Limite conhecido: o marcador protege contra acidente (usar uma pasta `repo` que já existia), não contra quem tem acesso de escrita ao seu state-dir (B5: com esse acesso, forjar o marcador, o `state.json` ou o `.git/config` já seria possível; não é uma fronteira que a ferramenta defenda).
12. Sem rede no código da ferramenta; a única rede é o `git` do próprio usuário (clone/fetch/push) depois da confirmação. Sem token em arquivo: as credenciais são as que o seu `git` já usa.
13. **`--state-dir` validado sobre o caminho real.** A grafia crua é recusada se usar prefixo de caminho estendido/dispositivo do Windows (`//?/`, e as formas com barras invertidas `?` e `.`), caminho UNC (inclusive o administrativo `localhost` + `c$`) ou, no Windows, nome terminado em ponto ou espaço. Depois a ferramenta resolve o `realpath` do state-dir (ou do ancestral existente mais próximo, acrescentando o resto) e compara com o `realpath` da pasta pessoal do sistema e de `--home`: junction/link para a casa ou para a raiz de uma unidade, e nome 8.3 da casa, são recusados, assim como uma pasta que já é repositório git.
14. **O git nunca herda o diretório do processo.** Todo comando git roda com `cwd` explícito (o state-dir ou o clone; o `clone` roda no state-dir) e com `GIT_CEILING_DIRECTORIES` apontando para o pai do state-dir, além de `--git-dir`/`--work-tree` explícitos nos demais comandos: um state-dir dentro de um repositório seu não sobe para esse repositório (config, `insteadOf`, hooks) e ele não é tocado.
15. **Poda de `repo.velho-*` só do que é comprovadamente nosso:** exige pasta real, `.owner.json` válido com caminho coerente (`<state-dir>/repo`) **e** a cópia interna `.git/ai-usage-metrics-owner` igual ao id do marcador. Pasta com marcador forjado não é apagada. Se o marcador não puder ser movido ao aposentar um clone, a ferramenta **avisa**: a pasta velha fica sem marcador, nunca é podada e só acumula até você removê-la.

## Histórico, `history.json` e `restore`

- **O baseline (último `metrics.json` publicado) é entrada não confiável** e é validado estritamente antes de qualquer uso: teto de 5 MiB, allowlist do esquema v1, `schemaVersion` 1, `synthetic: false` e a barreira de privacidade. Inválido, adulterado ou sintético é **ignorado** com o aviso `histórico ignorado: …`, sem derrubar o export. O JSON final da mescla passa de novo pelo esquema e pela barreira de privacidade, e o `publish` ainda confere ferramentas, nomes e allowlist.
- **O baseline nunca amplia a lista de ferramentas nem a de projetos:** ids de ferramenta fora do registro de adaptadores em uso são descartados (com aviso) e nomes de projeto do baseline nunca entram (`projects` vem só dos registros locais). Só a série diária é mesclada, e ela já era pública.
- **`history.json`** fica no state-dir, é uma cópia do `metrics.json` publicado, é gravado só depois de um envio bem-sucedido (ou quando o conteúdo já estava publicado), com escrita atômica, modo `0600` (Linux/macOS; no Windows vale a ACL do perfil) e recusa de link simbólico no destino. O `metrics.json` do clone local só é usado se o clone for nosso (marcador de posse e as demais checagens do item 8 das travas); essas checagens não foram relaxadas.
- **`restore` é uma etapa de rede** e pede confirmação (`[s/N]` em terminal ou `--yes`; sem terminal e sem `--yes`, não faz nada). Reaproveita exatamente a maquinaria do `publish` (remoto validado, ambiente do git por allowlist, protocolos permitidos, clone marcado, `cwd` explícito, hooks desligados, sem token) e só lê: nunca faz commit nem push. `restore --from-file` é 100% offline e valida do mesmo jeito.
- **Limitações:** os dados são autodeclarados e o histórico é **tão confiável quanto o repositório de dados do próprio usuário**: quem consegue escrever nele (ou no seu `history.json`) consegue inflar a série; a ferramenta só garante o formato, não a verdade. A mescla por máximo nunca reduz um número, então um baseline inflado se propaga até você apagar o `history.json` e corrigir o repositório. Detalhes: [`docs/historico.md`](docs/historico.md).

## SVGs: modelos e cores

- **Lista fixa de arquivos.** O `publish` só escreve, adiciona ao git (`git add` com a lista explícita, nunca `-A`) e envia os 5 arquivos acima. As checagens existentes valem para cada um: recusa de link simbólico (no disco e no repositório remoto, modo `120000`), escrita atômica e clone sem alterações inesperadas. O dry-run lista os 5 e o diff de cada um.
- **SVGs regerados e verificados.** Os 4 SVGs são sempre gerados de novo, no `publish`, a partir do JSON já validado (um SVG que esteja no disco nunca é enviado) e **cada um** passa pela barreira de privacidade antes de ser gravado no clone ou enviado. O `render` faz o mesmo antes de gravar. Os modelos não têm script, fonte, imagem nem link externo, e todo texto é escapado.
- **Validação estrita de cor.** `colors`, `colorsDark` e `tools` aceitam somente `#rgb` ou `#rrggbb` (regex ancorada; nomes de cor, `rgb()`, `hsl()`, `var()`, `url()`, `;`, `}`, `<`, comentários CSS, espaços, `!important`, vazio e tipos errados são recusados). Chaves desconhecidas e ids de ferramenta fora do registro de adaptadores também. O valor é normalizado (minúsculas, 6 dígitos) e só então entra no CSS do SVG. A validação roda na carga da configuração e **de novo** no renderizador; a escala de calor é calculada no código e sempre escrita em hexadecimal. Há testes de injeção (`red;}</style><script>`, `url(javascript:...)`, `#fff"/><script`, comentários CSS).
- **Legibilidade não é verificada**: não há ajuste automático de contraste; escolher cores legíveis é responsabilidade de quem configura.

## E-mail do commit (histórico público)

O commit enviado ao seu repositório público leva um autor e um committer. A ferramenta **não usa** a identidade global do seu git: usa `commitName` (padrão: `githubUser`) e `commitEmail` (padrão: `<githubUser>@users.noreply.github.com`), passados ao git por `-c user.name/user.email` e pelo ambiente.

- O dry-run mostra o autor que será usado.
- Se o e-mail **não** terminar em `@users.noreply.github.com`, o dry-run avisa em destaque e o envio exige confirmação extra: em terminal, digitar a frase pedida (mesmo com `--yes`); sem terminal, a flag `--accept-public-email`; no modo automático, fica **bloqueado**.
- O formato com ID numérico também vale, e pode ser o que o GitHub exige da sua conta: `ID+usuario@users.noreply.github.com` (veja o seu em GitHub > Settings > Emails). Exemplo no `config.json`:
  `"commitName": "Seu Nome", "commitEmail": "12345678+seu-usuario@users.noreply.github.com"`.
- Se a opção "Block command line pushes that expose my email" estiver ligada na sua conta, o GitHub recusa pushes com e-mail privado: use o noreply.

## Publicando uma nova versão (mantenedor)

1. Rode `npm test` e `npm run lint`.
2. Rode `npm pack --dry-run` e confira a lista de arquivos (só `bin`, `src`, `docs`, `templates`, `examples`, `LICENSE`, `README.md`, `SECURITY.md` e `package.json`): nada de `.env`, `config.json`, `state.json`, `out/`, `repo/` ou logs.
3. Publique com **2FA** ativo na conta do npm. O `--provenance` só é gerado a partir de um CI suportado (por exemplo GitHub Actions com `id-token: write`); de uma máquina local ele falha, e nesse caso publica-se sem ele, com 2FA.
4. Atualize `AI_USAGE_METRICS_VERSION` no template do Actions. As ações do template estão fixadas por SHA de commit (resolvidas com `git ls-remote` nas tags `v4.2.2` e `v4.1.0`); ao atualizar uma ação, repita a consulta e troque o SHA.

## Riscos que continuam com você

- **Política de host é léxica:** ela olha o texto do nome (sem ponto, `localhost`, `.local`, IP, rótulo numérico...), não resolve DNS. Um domínio público que resolva para 127.0.0.1 ou para a rede interna passa. Confira o host no dry-run.
- **Um clone nosso pode perder commits locais não enviados** quando é recriado: o commit local fica na cópia `repo.velho-*` (e no reflog dela), mas não no novo clone. Só as 3 cópias mais recentes são mantidas.
- **O envio agendado falha enquanto houver uma pasta `repo` que não é nossa** (por exemplo, clone de uma versão anterior da ferramenta, sem marcador), sem alterar nada, até um humano renomear/mover essa pasta ou escolher outro `--state-dir`.
- O `~/.gitconfig` (e o `/etc/gitconfig`) continuam valendo: `url.<x>.insteadOf`/`pushInsteadOf`, `credential.helper`, `core.sshCommand` e afins são seus e a ferramenta não os desativa. O dry-run mostra a URL **aprovada**, mas o git pode reescrevê-la (um `insteadOf` global pode levar o push a outro destino). Confira o seu `git config --global --list` antes do primeiro envio.
- O histórico de um repositório público é permanente e pode ser clonado. Confira o dry-run antes do primeiro envio.
- Datas, volume de uso e ranking são informação pública, mesmo com projetos anonimizados. Pouca atividade em um dia pode revelar rotina.
- O nome público de um projeto pode revelar trabalho confidencial: só inclua o que você já divulga.
- Os números são autodeclarados e aproximados.
- O comando `report` mostra nomes reais de projetos no terminal: não cole a saída em lugares públicos.
- No Windows o log do agendador não existe (a tarefa não grava log); o modo `0600` do log só se aplica a Linux/macOS (`umask 077` no comando de cron impresso, **não validado**). O `schtasks` grava o caminho do Node usado na criação da tarefa: recrie a tarefa se atualizar ou mover o Node.
- Só foi validado no Windows (o do autor). macOS/Linux não foram testados (inclusive os modos `0700`/`0600`, o `cron` impresso e o `schtasks`/`cron` reais: os comandos são só impressos e nenhuma tarefa agendada foi criada nos testes).

## Reportar um problema de segurança

Envie um e-mail para **dev.brenoluiz@gmail.com** com o assunto "ai-usage-metrics: segurança", descrevendo o problema e como reproduzi-lo. **Não publique detalhes de uma falha em uma issue pública** antes de ela ser corrigida.

Quando o repositório existir no GitHub, vale também ativar o aviso privado de vulnerabilidade (Settings > Security > "Private vulnerability reporting") como segundo canal.
